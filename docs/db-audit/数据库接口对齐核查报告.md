# 数据库接口对齐核查报告

> 核查对象：`career-system-back/backend/database_interface.py`
> 核查基准：本机 SQL Server 实际库结构（只读查询）+ `database/createtable(1).sql` + 调用方代码
> 核查方式：逐表、逐字段、逐方法比对，并用真实连接执行接口原有 SQL 验证
> **本报告只做核查，未修改任何代码、SQL 或数据库对象。**

---

## 一、结论摘要（先看这 6 条）

1. **本机存在两个库，不是"一个库结构不对"这么简单。**
   - `career_recommendation`：15 张表，接口代码就是照它写的（20 学生 / 23 岗位 / 93 条匹配）。
   - `career_system`：24 张表，`createtable(1).sql` 按规范化重设计的库（1 用户 / 1 学生 / 3 岗位）。
   - 接口默认连的是 `career_recommendation`，但应用账号 `app_user` **登录失败**；`app_user` 实际能连的是 `career_system`。

2. **实测结果（决定性证据）：接口的 26 条典型 SQL 在真实库上执行——**
   - 对 `career_recommendation`：**只有 2 条失败**，都是表名不存在（`holland_test_results`、`career_values`）。其余表名、列名全部命中。
   - 对 `career_system`：**26 条全部失败**，14 张逻辑表在库里一个都不存在。

   逐字段判定汇总（91 个字段，见附录 B 的 CSV）：
   **✅ 可直接改名 42 个 · ⚠️ 需语义/类型转换 15 个 · ❌ 无可匹配项 22 个 · ⛔ 需结构重建 12 个**。

3. **所以"只改名字"只对 `career_recommendation` 成立**：需要改的是 **2 个表名 + 2 个字段名**（`work_values.worth_id / worth_test_time`）。
   对 `career_system` 则**不是改名问题**：9 张表可改名映射，3 张表是结构重建（列变行 / 一表拆三表 / 一表拆主从），2 张表根本没有对应表。

4. **两个库都缺自增主键，这是改名解决不了的硬阻塞。**
   `createtable(1).sql` 明明写了 `IDENTITY(1,1)`，但实库中 `career_system` **没有任何一列是自增**；`career_recommendation` 同样没有。
   而接口 15 个 INSERT 全部**不写主键**，依赖数据库自增 → 插入时必然报"不能将 NULL 值插入列 'xxx_id'"。也就是说：即使表名全改对，**注册、加学生、加技能、加测评、加计划、加匹配结果、加经历，全部写不进去**。

5. **两个库现有的账号密码都与接口的哈希算法不兼容。**
   接口用 SHA-256（64 位十六进制）。旧库 `password_hash` 实测长度 9，新库长度 40 → `verify_password` 必然返回 False。**现有账号一个都登不进去**；而新注册又被第 4 条卡死。

6. **数据库目前其实没有被系统真正使用。**
   50 个业务方法里只有 **6 个**被 API 调用（全是登录/注册/资料），其余 44 个无调用方；推荐、课程、实习、职业规划、日/周计划全部走 `sample_data.py` 写死数据与 `MEM_PLANS/MEM_TASKS` 内存字典。连库失败后接口会静默回退内存模式，所以系统"能跑"但没落库。

### 2.3 三个必须先知道的结构事实

**① 两个库都没有自增列（`IDENTITY`）**
`createtable(1).sql` 写的是 `INT IDENTITY(1,1)`，但实库 `COLUMNPROPERTY(...,'IsIdentity')` 查询结果为 0 条。旧库也一样。两库均**无触发器**可代发主键。
→ 接口所有"不写主键的 INSERT"都会失败，与表名无关。

**② 两库主键 ID 体系互不相通，且还有第三套**
- 旧库：`student_id` = 2400001 起（人工编号）
- 新库：`student_id` = 1
- 接口兜底常量：`DEFAULT_STUDENT_ID = '2024001'`（`backingend_API.py:48`），来自 `sample_data.py`
→ 推荐接口拿 `'2024001'` 去匹配，与任何库的主键都对不上；且 `resolve_student_id()` 在用户没有关联学生时直接兜底到这个常量，**所有账号看到的是同一个样本学生**。

**③ 接口从未真正拿到"用户→学生"的关联**
`resolve_student_id()` 读 `user.get('student_id')`（`backingend_API.py:66`），但 `users_login` 与 `user` 两张账户表**都没有 `student_id` 列**（关联应经 `students` / `student_info`）。
→ 登录返回的 `student.student_id` 永远是 `None`；前端 `user.studentId` 永远 `undefined`。

## 三、接口的实际使用面

### 3.1 调用链

```
前端 authService.ts
  login    → POST /api/auth/login    → db.get_user_by_username / get_user_by_email → db.update_user_last_login
  register → POST /api/auth/register → db.add_user
  profile  → GET  /api/auth/profile  → db.get_user_by_id
  reset    → POST /api/auth/reset-password → db.get_user_by_email / update_user_password

推荐三接口 → sample_data.get_student_profile / get_filtered_jobs（不查库）
职业规划  → MEM_PLANS（内存字典，不查库）
计划任务  → MEM_TASKS（内存字典，不查库）
```

- 业务方法总数：**50**；被 API 调用：**6**；无调用方：**44**。
- 也就是说：`get_student_*`、`add_skill_*`、`get_day_plan_*`、`get_holland_*` 等 44 个方法目前是"写了但没接线"，**改它们不影响当前页面，但会影响后续接库**。

### 3.2 当前真实运行状态

1. `DatabaseInterface.__init__` 用 `app_user` 连 `career_recommendation` → 失败 → `use_sqlserver=False`；
2. 所有 `db.*` 调用走内存字典：`self.users = {}`（空）、`self.students = {}`（空）；
3. 因此**登录必失败、注册"成功"但只存在进程内存里、重启即丢**；
4. 推荐仍能返回结果，因为完全没走 db，走的是 `sample_data`。

## 四、逐表逐字段核对

判定口径：
- ✅ **直接改名可对齐**：语义、类型、约束一致，只需换表名/列名
- ⚠️ **需语义或类型转换**：字段能对上，但值域/单位/类型不一致，改名前必须定转换规则
- ⛔ **需结构重建**：不是一列对一列，涉及拆表、主从、列转行
- ❌ **无可匹配项**：目标库没有承载该语义的列/表，需要补设计

### 4.1 `users_login`（账户） → `user`

| # | 接口字段 | 语义与关联 | 使用方法（行号） | 旧库 `career_recommendation` | 新库 `career_system` | 判定 |
|---|---|---|---|---|---|---|
| 1 | `user_id` | 账户主键；写入 JWT；每次鉴权按此取用户；前端 `user.id` | `get_user_by_id`(252)、`token_required`(64)、`add_user`(281) | `users_login.user_id` int，非自增 | `user.user_id` int，非自增 | ⚠️ 名称一致，但插入无自增 |
| 2 | `user_name` | 登录名。前端把**邮箱**当 username 传（`authService.ts` login payload）；旧库存量值是 `stu_0001` 这类账号 | `get_user_by_username`(186)、`add_user`(281) | `users_login.user_name` nvarchar(50) ✅ | **无此列**，`user` 只有 `email` | ❌ 新库无用户名；语义待定（见 5.1） |
| 3 | `password_hash` | SHA-256 十六进制 64 位 | `add_user`(281)、`update_user_password`(338) | nvarchar(**20**) → 存 64 位会触发截断错误 | varchar(255) ✅ | ⚠️ 旧库列宽不足；新库类型够但存量值不是 SHA-256 |
| 4 | `user_email` | 邮箱，唯一；前端资料页 `email` | `get_user_by_email`(208)、`add_user`(281) | `users_login.user_email` ✅ | `user.email`（唯一约束） | ✅ 改名 |
| 5 | `user_status` | 账号启用状态，默认 1 | `add_user`(281) | ✅ tinyint 默认 1 | **无此列** | ❌ |
| 6 | `user_created_time` | 注册时间 | `add_user`(281) | ✅ datetime2 | `user.create_time`（默认 GETDATE） | ✅ 改名 |
| 7 | `last_login_time` | 最后登录时间 | `update_user_last_login`(316) | ✅ `last_Login_time`（大小写不敏感，不构成问题） | `user.last_login_time` ✅ | ✅ 改名 |
| 8 | `user_remark` | 备注 | `add_user`(281) | ✅ nvarchar(500) | **无此列** | ❌ |
| 9 | `student_id`（读取，非表列） | 期望由账户直接带出学生 ID → 前端 `studentId` | `resolve_student_id`(72)、`get_profile`(798) | **无此列**，`students.user_id` 才是关联 | **无此列**，`student_info.user_id` 才是关联 | ❌ 两库都需 JOIN 取得 |

**关联链**：`user_id` → `students.user_id` / `student_info.user_id`（1:1，`student_info` 上还有唯一约束 `UQ_student_user`）。
**本表结论**：旧库 8 个真实列全命中，唯一表名不同；新库缺 3 列（`user_name`、`user_status`、`user_remark`），`student_id` 两库都需通过关联表取。

## 五、没有可匹配项的字段：本该是什么

以下是"改名改不出来"的部分，逐条给出**它是什么、关联到哪、本该有什么**。

### 5.1 `users_login.user_name / user_status / user_remark`
- **它是什么**：登录名、账号状态（启用/禁用）、备注。
- **关联**：`user_name` 被登录接口直接当查询键；前端其实传的是邮箱。
- **新库现状**：`user` 表只有 `email`，没有用户名、状态、备注。
- **本该是**：`user` 表补 `username VARCHAR(50) NULL`（可空，登录时 `email` 或 `username` 二选一）、`status TINYINT DEFAULT 1`、`remark VARCHAR(500) NULL`；或**明确废弃用户名**，把 `get_user_by_username` 改为按 `email` 查询（与前端行为一致，改动最小）。
- **不可猜的点**：旧库存量 `user_name` 是 `stu_0001`，不是邮箱，二者不是同一语义。要么接受"登录名与邮箱分离"，要么迁移数据。需你定。

### 5.2 `companies` 整表（`company_id / company_name / company_location / company_size / company_description`）
- **它是什么**：招聘企业主数据；`jobs.company_id` 的父表。
- **关联**：`jobs → companies`；`matching_results` 展示公司名要靠 `jobs → companies` 两跳。
- **新库现状**：没有企业表；`job_library` 只挂 `industry_id`。
- **本该是**：新增
  `company(company_id PK, company_name, company_location, company_size, company_description)`，
  并在 `job_library` 增加 `company_id INT NULL FK → company(company_id)`。
- **明确反对**：不要用 `industry_id` 冒充 `company_id`。行业（互联网/金融科技）与企业（字节跳动）是两级概念，顶替会让"按公司看岗位"永久失效。

### 5.3 `student_preferences` 整表（4 个业务字段）
- **它是什么**：意向行业（多选）、意向城市（多选）、期望薪资、工作方式。
- **关联**：推荐算法用 `preferred_industries` 算匹配度；`student_id` 1:1。
- **新库现状**：只有 `student_info.desired_industry_id`（单值）与 `desired_location`（单值）。
- **本该是**：新增
  `student_preference(preference_id PK, student_id FK UNIQUE, preferred_industries NVARCHAR(MAX), preferred_locations NVARCHAR(MAX), expected_salary NVARCHAR(50), work_mode_preference NVARCHAR(20))`；
  若坚持规范化，可拆 `student_preferred_industry(student_id, industry_id)` 与 `student_preferred_location(student_id, city)` 两张关联表——但那是更大的改动，需你选。

### 5.4 `student_skills.experience_months` + `student_id`
- **它是什么**：某项技能练了几个月；以及这条技能记录属于哪个学生。
- **关联**：`student_skills` 是"学生—技能"多对多；`student_id + skill_id` 唯一。
- **新库现状**：`skill_assessment_detail` 只有 `proficiency_level`、`self_score`，没有经验月数；`student_id` 在主表 `skill_assessment` 上，明细表查不到。
- **本该是**：`skill_assessment_detail` 增加 `experience_months INT NULL`；或保留一张 `student_skill(student_id, skill_id, proficiency_level, experience_months)` 汇总表（推荐，因为"当前技能水平"与"历史评估明细"是两种数据，混在一张表会导致每次评估都覆盖不了、越查越多）。

### 5.5 `experiences.experience_type / experience_title / experience_content / experience_role / updated_time`
- **它是什么**：一段经历的类别、标题、正文、角色、更新时间。
- **关联**：`student_id → 学生`；前端简历页按类型分组展示。
- **新库现状**：被拆成 `internship_experience`、`project_experience`、`campus_activity` 三张表，各自字段名不同（`position` / `project_name` / `campus_role`；`description` / `description` / `responsibility`），没有任何一列表示"类型"，也没有 `updated_time`。
- **本该是**：二选一——
  (a) 保留三张表，另建视图 `v_experience` 把三表 `UNION ALL` 成统一结构（`experience_type` 用常量 `'internship'/'project'/'campus'` 生成），接口只读写视图；
  (b) 合成一张 `experience(experience_id, student_id, experience_type, experience_title, experience_content, experience_role, start_date, end_date, updated_time)`，三张专表降级为可选扩展。
  选 (a) 改动小但写入仍要路由；选 (b) 接口几乎不用改，但要迁移现有 3 条数据。

### 5.6 `career_values` 的 6 个维度列
- **它是什么**：社会贡献、成就导向、安全稳定、工作生活平衡、权力地位、创新挑战，6 个 0–100 分。
- **关联**：`job_value_requirement.value_id` 用同一套价值观字典做岗位要求匹配。
- **新库现状**：`values_library` 只有 5 条（技术成长、创新性、稳定性、薪资回报、社会价值），且与接口 6 个维度**不是同一套词表**；分值是 `value_assessment_detail.score` 的**行**，不是列。
- **本该是**：先把 `values_library` 词表统一成接口的 6 个维度（或明确映射：社会价值↔社会贡献、稳定性↔安全稳定、创新性↔创新挑战…），再由接口写 1 条 `value_assessment` + 6 条 `value_assessment_detail`。
- **为什么不能只改名**：这是"列 → 行"的模型变化，SQL 形态从 `INSERT 6 列` 变成 `INSERT 1 主 + 6 明细`，且必须先查字典拿 `value_id`。

### 5.7 `job_skill_requirements.requirement_type`
- **它是什么**：该技能是"必需"还是"加分"。
- **关联**：推荐算法用它给技能缺口加权。
- **新库现状**：`job_skill_requirement` 只有 `required_level`，没有类型。
- **本该是**：`job_skill_requirement` 增加 `requirement_type VARCHAR(10) NULL`（值域：必需/加分）。

### 5.8 `jobs.salary_range` / `jobs.company_id`
- **本该是**：见 5.2；`salary_range VARCHAR(50) NULL` 应加在 `job_library` 上（或单独 `job_salary` 表，若要做结构化区间）。

### 5.9 `weekly_task` 的完成度语义
- **它是什么**：周计划是否完成（接口 0/1）。
- **新库现状**：`completion_percentage TINYINT`（0–100）。
- **本该是**：二者取一。若保留百分比，接口写 0/100，读时 `>0` 视为进行中、`=100` 视为完成；否则加 `is_completed BIT`。

### 5.10 两边都缺的"日→周"归属
- **它是什么**：一条日任务属于哪个周计划。
- **新库现状**：`daily_task.weekly_task_id` 有，接口完全不写（`add_day_plan` 不传）。
- **本该是**：接口补 `weekly_task_id` 入参与字段；旧库没有这个关系，属旧库设计缺失。

### 6.2 查询类：会静默返回空

## 七、两条对齐路线（请选一条，我再动手）

### 路线 A：对齐到 `career_recommendation`（旧库，改动最小）
**只需要改 4 处名字：**
1. `holland_test_results` → `holland_tests`
2. `career_values` → `work_values`
3. `work_values.value_id` → `worth_id`（`add_career_values` 的返回键）
4. `work_values.value_test_time` → `worth_test_time`（`add_career_values` 的插入列、排序键）

**但还必须同时解决 3 个非改名问题：**
- 给 15 个 INSERT 补主键（改为 `SELECT ISNULL(MAX(id),0)+1` 或给表加 `IDENTITY`）——**推荐加 IDENTITY，不改代码**；
- `users_login.password_hash` 从 `nvarchar(20)` 扩到 `nvarchar(64)` 以上（否则注册必报截断）；
- 给 `app_user` 授予 `career_recommendation` 的访问权限，或把连接参数改成可用的库。

**优点**：14 张表全在、数据现成（20 学生/23 岗位/93 匹配）、接口 44 个未接线方法也能直接用。
**缺点**：与 `createtable(1).sql` 的设计不一致，论文里"规范化设计"与"实际实现"会对不上；且旧库没有 `values` 词表、没有行业表、没有测评明细。

### 路线 B：对齐到 `career_system`（设计库，改动大）
**不是改名，是重写 6 张表的读写：**
- 改名即可：`user`、`student_info`、`skill_library`、`holland_assessment`、`daily_task`、`weekly_task`、`job_library`、`job_skill_requirement`、`job_match`（9 张）
- 结构重建：`career_values`（1 主 + 6 明细）、`experiences`（按类型路由三表）、`student_skills`（主从）
- 需补表：`company`、`student_preference`
- 需补列：`user.username/status/remark`、`skill_assessment_detail.experience_months`、`job_library.company_id/salary_range`、`job_skill_requirement.requirement_type`、三张经历表的 `updated_time`
- 仍需解决：两库都无 IDENTITY、现有账号哈希不兼容、`DEFAULT_STUDENT_ID` 体系不符

**优点**：与设计文档一致，论文/答辩口径统一；`holland_code`、`industry`、`study_time`、`certificate` 等能力更完整。
**缺点**：改动面约为路线 A 的 8–10 倍；现有数据只有 1 个学生，需要重新灌数据。

## 八、需要你确认的 4 件事

1. **基准库选哪个？** `career_recommendation`（旧、数据全、改 4 处名）还是 `career_system`（新、设计一致、需重写）？
