### T3 账号登录可用性（本次不处理）

迁移后系统内账号状态：

| 来源 | 数量 | 密码存储 | 能否登录 | 原因 |
|---|---|---|---|---|
| 新库保留账号 | 1 | `$2y$10$EXAMPLEHASHEXAMPLEHASHEXAMPLEHASH`（40 字符，占位串非真实 bcrypt） | **否** | 接口用 `sha256(明文)==存储值` 严格比对，SHA-256 输出 64 位十六进制，永不等于该串 |
| 旧库 `users_login` | 20 | 明文 `passwd123`（9 字符） | **否** | 同上，`sha256('passwd123')` ≠ `'passwd123'` |

**结论**：两库账号没有一个能通过当前登录校验。「老账号不迁移」实际零损失。

**要让账号可用，三选一**：
1. 走注册流程新建（`hash_password` 会正确写入 SHA-256）
2. 手工执行 `UPDATE users_login SET password_hash = <sha256(密码)> WHERE user_id = 1`
3. 改登录逻辑兼容多算法（不推荐，破坏最小改动原则）

### T4 计数器归位（本次执行，作为脚本最后一步）

迁移迁入旧 ID 后，对下列表执行 `DBCC CHECKIDENT('表名', RESEED, 该表当前 MAX(id))`：

| 表 | 主键 | 迁入后 MAX(id) | 归位目标 |
|---|---|---|---|
| `skills` | skill_id | 2400025 | 2400025 |
| `companies` | company_id | 2400010 | 2400010 |
| `students` | student_id | 2400020 | 2400020 |
| `jobs` | job_id | 2400025 | 2400025 |
| `job_skill_requirements` | requirement_id | 2400150 | 2400150 |
| `matching_results` | match_id | 2400100 | 2400100 |
| `student_skills` | skill_record_id | 2400040 | 2400040 |
| `student_preferences` | preference_id | 2400020 | 2400020 |
| `users_login` | user_id | 1（不迁旧账号） | 1 |
| `experiences` | experience_id | 0 或 3 | 0 或 3 |
| `holland_test_results` | holland_test_id | 0 | 0 |
| `week_plans` | week_plan_id | 0 | 0 |
| `day_plans` | day_plan_id | 0 | 0 |

> `DBCC CHECKIDENT(t, RESEED, N)` 的语义是「下一个插入值为 N+1」。空表 RESEED 0 → 下一个从 1 开始。
> 归位仅影响编号连续性（避免从 2401001 起跳），无功能影响。

## 四、本轮新发现 / 更正（相对 08 号文档）

### 发现 1：接口有 **2 张表**在旧库不存在 —— 不止 1 张

逐条静态核对接口 49 条 SQL 的表名与列名后，旧库缺失的是两张表、共 4 条 SQL：

| 接口引用的表 | 出现行号 | 旧库实际 | 差异 |
|---|---|---|---|
| `career_values` | 620（SELECT）、632（INSERT） | 无此表，只有 `work_values`（0 行） | 表名不同；列名 `value_test_time` vs `worth_test_time` |
| `holland_test_results` | 580（SELECT）、592（INSERT） | 无此表，实际叫 `holland_tests`（0 行） | **仅表名不同**，列名（`holland_test_id`/六维/`holland_test_time`）完全一致 |

加上 `get_user_by_studentname` 的 `WHERE )` 语法残缺（行 230），旧库上**共 5 条 SQL 跑不通**，分属 3 类原因。

> 早前只报了 `career_values` 一张，漏了 `holland_test_results`。此处更正。
> 影响判断：旧库并非「14 张表全适配」，而是 **12/14** 表名能对上（缺 holland 与 values 两张）；新库则是 0/14（全部需改名）。
> 这两张表迁移后都会补齐（`holland_assessment → holland_test_results` 改名；`career_values` 由 T1 接口适配承接），故不影响迁移方案，只影响「旧库更适配」这句判断的准确度。

### 更正 2：旧库 `experiences.experience_id` 本身就是 IDENTITY

08 号文档称「旧库非自增是潜在 bug，新建即修正」——**该结论错误**。
实测 `sys.columns.is_identity = 1`，旧库该列就是自增。新建表照抄 IDENTITY 即可，不构成「修正」。

### 更正 3：脚本把列名写成 `worth_test_time`，接口要的是 `value_test_time`

`run_migrate_v2.py:218` 把 `test_time` 改名为 `worth_test_time`（照 `work_values` 抄的），但接口 `ORDER BY value_test_time`。若按原方案执行，该查询会报「列名无效」。
因本轮决策「价值观库不动」，此问题随阶段 7 一并删除；但 T1 实现时必须用 `value_test_time`。

### 更正 4：前端不是「只有路由和标签」，页面是完整的，只是不发请求

实测：`app/assessment/values/page.tsx` **674 行**、`app/assessment/holland/page.tsx` **461 行**，均为完整交互实现；两文件内 `fetch(` / `axios` / `/api/` 出现次数**均为 0**。
全前端仅出现 1 个后端路径 `/api/upload`。

准确表述：**页面齐全、纯前端运行、测评结果不落库**。因此 T1 改造不触及现有功能，但「前端没做」这个说法是错的。

### 更正 5：接口 SQL 不是 58 条，实测 50 处 `query =` 赋值

| 统计口径 | 数量 |
|---|---|
| `query =` 赋值（逐行扫描） | **50 处**（49 条静态字符串 + 1 条 f-string 动态拼接，行 947） |
| `_execute_query` + `_execute_update` 调用 | 53 次（27 + 26） |
| `def` 总数 | 56 个（51 业务方法 + 5 辅助方法） |

「58 条 SQL」这个数字在 01/02/03/04 多份文档中沿用，但在当前代码上**无法复现**（各种口径都凑不出 58），来源已不可考。今后以本表为准，停止使用 58 这个数。
