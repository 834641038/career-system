## 1 先理解业务：新库这 24 张表到底在讲什么

新库不是"旧库改了个名字"，它是另一套粒度更细的建模。按业务域拆开看：

| 业务域 | 表 | 在回答什么问题 |
|---|---|---|
| **账户** | `user`、`student_info` | 谁在用系统；这个人的学号、专业、年级、GPA、所在地 |
| **测评** | `holland_assessment`（兴趣六维）、`skill_assessment` + `skill_assessment_detail`（技能测评，主从）、`value_assessment` + `value_assessment_detail` + `values_library`（价值观，主从 + 词典） | 这个学生"是什么样的人"——兴趣、技能、价值取向，且**每次测评留一份历史** |
| **能力字典** | `skill_library` | 系统认识哪些技能 |
| **经历** | `internship_experience`、`project_experience`、`campus_activity`、`certificate`、`achievement`、`competition_award` | 实习、项目、校园活动、证书、获奖、成就——**每一类一张表** |
| **目标侧** | `industry`、`job_library`、`job_skill_requirement`、`job_value_requirement`、`job_match` | 有哪些行业/岗位，岗位要什么技能和价值观，算出来的匹配分 |
| **计划** | `career_plan`（长期）→ `weekly_task`（周）→ `daily_task`（日）、`study_time`（学习时长） | **三层计划**，长期计划拆到周、周拆到日，另记学习投入 |

**这套设计的取向是"一次测评 = 一条主记录 + N 条明细"**，而旧库（原型库）的取向是"一人一行、六个维度就是六列"。两者不是对错，是粒度不同：

| | 旧库 `career_recommendation`（原型） | 新库 `career_system`（设计） |
|---|---|---|
| 定位 | **已灌满数据的可运行原型**：20 学生 / 23 岗位 / 93 条匹配 | **写好但没用过**：1 学生 / 3 岗位 / 2 条匹配 |
| 价值观 | 一张宽表 6 列 | 主表 + 明细 + 词典（列转行） |
| 经历 | 一张表 + `experience_type` 字段 | 6 张表按类型拆开 |
| 计划 | 日计划、周计划两张平表 | 长期→周→日三层 |
| 意向 | 多值文本（`互联网,人工智能`） | 单值 FK（`desired_industry_id`） |
| 企业 | 有 `companies` 9 家 | **没有企业表**，岗位只挂 `industry_id` |

**这就是本方案要解决的核心矛盾**：接口（`database_interface.py`）是照着旧库的粒度写的，它要"宽表、单经历表、两层的日/周计划"；新库给的是"明细表、6 张经历表、三层计划"。所以这不是改名字，是**在两种粒度之间做一次映射**。

## 2 接口到底要什么：14 张表的硬契约

不是猜的，是从 `database_interface.py` 的 57 条 SQL 里反解出来的。三条容易被忽略的硬约束：

1. **`SELECT *` 用得很多**（`get_student_by_id`、`get_all_jobs`、`get_day_plan_by_id`…）→ 表里**多几列完全无害**，少一列就报错。这是好消息：新库那些"论文要多写"的列（性别、生源、绩点、期望毕业时间）**不用删**。
2. **`INSERT` 的列是写死的**（如 `INSERT INTO students (student_major, user_id)` 只写 2 列）→ 表里**任何 NOT NULL 且无默认值的列，都会让这条 INSERT 失败**。这是唯一的"不能多"的地方。
3. **JOIN 写死了表名和列名**（`ss JOIN skills s ON ss.skill_id = s.skill_id`）→ 被 JOIN 的表和列名必须一字不差。

接口认定的 14 张表与关键列：

| 表 | 接口用到的列 | 特别要求 |
|---|---|---|
| `users_login` | `user_id, user_name, password_hash, user_email, user_status, user_created_time, last_login_time, user_remark` | 还要求 `SELECT *` 能带出 **`student_id`**（`resolve_student_id()` 读的就是它） |
| `students` | `student_id, student_name, student_major, grade, gpa, user_id` | `grade` 参与算法（年级区间），必须是数字 |
| `companies` | `company_id, company_name, company_location, company_size, company_description` | `get_matching_results` 靠它 JOIN 出公司名 |
| `skills` | `skill_id, skill_name, skill_category, skill_description` | 被 3 张表 JOIN |
| `holland_test_results` | `holland_test_id, student_id, holland_R/I/A/S/E/C, holland_test_time` | 按 `holland_test_time DESC` 取最新 |
| `career_values` | `value_id, student_id, social_contribution, achievement_oriented, safe_stable, work_life_balance, power_status, innovation_challenge, value_test_time` | **宽表 6 列**，不是明细 |
| `experiences` | `experience_id, student_id, experience_title, experience_content, experience_type, experience_role, experience_start_time, experience_end_time, updated_time` | **一张表 + type 字段** |
| `day_plans` | `day_plan_id, student_id, day_plan_name, day_plan_describe, day_plan_prority, day_plan_ddl, day_plan_finish` | `day_plan_ddl >= DATEADD(...)` → 为 NULL 的行会被静默丢掉 |
| `week_plans` | `week_plan_id, student_id, week_plan_name, week_plan_start, week_plan_ddl, week_plan_finish` | 同上 |
| `student_skills` | `skill_record_id, student_id, skill_id, proficiency_level, experience_months` | 按 `(student_id, skill_id)` 增删改；要 JOIN `skills` |
| `jobs` | `job_id, company_id, job_title, job_type, salary_range` | `company_id` 关联 `companies` |
| `job_skill_requirements` | `requirement_id, job_id, skill_id, required_level, requirement_type` | `required_level` 是数字（与算法 1–5 同尺度） |
| `student_preferences` | `preference_id, student_id, preferred_industries, preferred_locations, expected_salary, work_mode_preference` | 一人一条，先查后 UPDATE/INSERT |
| `matching_results` | `match_id, student_id, job_id, match_score` | JOIN `jobs` + `companies` |

## 4 四处"改名解决不了"的结构冲突（要你拍板）

### 4.1 价值观：明细表 vs 宽表　→ 建议「宽表 + 历史明细并存」

- 现状：`value_assessment`(1) → `value_assessment_detail`(5) → `values_library`(5)
- 接口要：`career_values` 一张宽表 6 列
- **做法**：把 `value_assessment` 改名成 `career_values` 并加 6 列，从明细转置回填；`value_assessment_detail` 保留，定位改成"历史明细/逐项打分"。
- 代价：同一份分数存在两处（宽表快照 + 明细）。**若只写宽表，明细会逐渐过期。**
- 备选：删掉 `value_assessment_detail` 与 `values_library`，只留宽表（更干净，但论文里"规范化"的论据没了）。

### 4.2 经历：6 张表 vs 1 张表　→ 建议「合并 3 张为 experiences，另 3 张保留」

- 现状：`internship_experience` / `project_experience` / `campus_activity` 三表结构高度重叠（起止 + 名称 + 描述 + 角色），另有 `certificate` / `achievement` / `competition_award` 三表（证书/获奖/竞赛，语义不同）。
- **做法**：只合并前 3 张进 `experiences`（用 `experience_type` 区分），后 3 张不碰（接口没有对应端点）。
- 代价：**同一段实习会有两份记录**（`experiences` 一条 + `internship_experience` 一条）。三种收尾方式：
  - **A（推荐）**：迁移后把 3 张表改名归档为 `_archive_internship` 等，不再写入 → 单一事实来源，论文里说明"原分表已归档"；
  - B：保留 3 张表继续写入，`experiences` 只作接口读写 → 双写，长期会不一致；
  - C：不合并，改用视图 UNION + INSTEAD OF 触发器 → 这就是你否掉的兼容层，不推荐。

### 4.3 技能：测评明细 vs 当前技能　→ 建议「并存，职责分开」

`student_skills`（当前值，一人一技能一行）与 `skill_assessment_detail`（某次测评的明细）不是重复，是"当前态 vs 历史态"。**推荐并存**，规则：接口只写 `student_skills`；`skill_assessment*` 只在重新测评时产生新历史。

### 4.4 意向偏好：单值 vs 多值　→ 必须新建，没有第二条路

新库的 `desired_industry_id` 是单值 FK，装不下"互联网,人工智能"。`student_preferences` 必须新建。`student_info` 上那两个单值字段**保留**（当作"首选"），两者关系：首选在 `student_info`，全量在 `student_preferences`。

## 5 实测发现的 5 个隐藏坑（不处理会直接失败）

### 5.1 `students` 的两个 NOT NULL + 唯一约束 → 注册必失败　【已解】

- 新库 `student_info.student_number`、`email` 都是 `NOT NULL` 且**唯一**。
- 接口注册只写 5 列（`student_name, student_major, grade, gpa, user_id`）→ 插入必报 `515 不能将 NULL 插入列`。
- 更隐蔽的：即使放宽为 NULL，**唯一约束在 SQL Server 里只允许一个 NULL**，第二个学生注册时就会撞唯一冲突。
- **解法**：改可空 + 把唯一约束换成**筛选唯一索引**（`WHERE ... IS NOT NULL`）。预演已验证可连续注册。

### 5.2 默认约束 / CHECK / 索引会挡住"删列"和"改类型"

- `daily_task.priority` 上挂着默认约束 `DF__daily_tas__prior__0C85DE4D` 和 CHECK，**直接 DROP COLUMN 会报 4922**；
- `daily_task.end_time` 在索引 `idx_daily_task_student_date` 里，**改 NOT NULL 前必须先拆索引**。
- 顺序必须是：删默认约束 → 删 CHECK → 删索引 → 加新列 → 迁值 → 删旧列 → 改名 → 重建索引。

### 5.3 ODBC 连接默认 `XACT_ABORT ON`：一句话失败，整笔事务回滚

预演时踩到的真实行为：中途一句 DDL 失败，前面所有改名**全部被回滚**。这对正式执行有两条含义：
- 好处：失败即全复原，不会留半成品；
- 要求：**必须分批提交**（一批一个事务），否则第 10 步失败会把第 1–9 步一起抹掉，排查困难。

### 5.4 `SCOPE_IDENTITY()` 在 pyodbc 参数化 INSERT 后不可靠　【接口隐患】

实测：参数化 `INSERT` 之后单独执行 `SELECT SCOPE_IDENTITY()`，返回的是**一批之前的旧值**（返回 3，实际新行是 6002）。接口 `register_user_with_student` 正是这个写法 → 注册出来的学生可能挂到**别人的 user_id** 上。
- **接口侧最小修复**：把 `INSERT` 改成 `INSERT ... OUTPUT INSERTED.user_id`（改 1 处，2 行）。
- 这条不在"改名"范围内，但**不改就是错的**，建议一起做。

### 5.5 值域映射不写死就会静默变形

`basic/proficient/expert`、`高/中/低`、`大二` 这些文本，如果直接塞进 `tinyint` 列而不做 CASE 映射，会变成 NULL 或 0，**不报错**，但数据全错。§3.4 的映射表就是为此存在的。
