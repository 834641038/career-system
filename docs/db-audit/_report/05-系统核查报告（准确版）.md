## 3. 账号与连接：这是「系统没连过库」的唯一根因

| 项 | 实测 | 取证 |
|---|---|---|
| 登录名 | `app_user`，SQL_LOGIN，**未禁用**，创建于 2025-12-07 | `sys.server_principals` |
| 默认数据库 | **`career_recommendation`** | 同上 |
| 在 `career_recommendation` 的映射 | **无**，角色为空 | `sys.database_principals` |
| 在 `career_system` 的映射 | 有，`db_datareader` + `db_datawriter` | 同上 |
| 用 `app_user` 连旧库 | **失败**：4060（无法打开请求的库）→ 18456 | 真实连接测试 |
| 用 `app_user` 连新库 | **成功** | 真实连接测试 |

**因果链**：连接串写死 `DATABASE=career_recommendation` → 该库无映射 → 4060 → `DatabaseInterface.__init__` 的 `except` 捕获 → `use_sqlserver=False` → `_init_sample_data()`。

这是**静默降级**：异常只被 `print` 出来，所以系统表面能跑，实际从未落库；降级后 `self.users={}`，注册登录全在进程内存，**重启即丢**。

## 4. 接口 SQL 逐条编译结果

方法：从 `database_interface.py` 抽全部 58 条 SQL，用 `sys.sp_describe_first_result_set` 编译（不执行、不写库），先 `USE` 目标库。

| 方法 | 报错 | 定性 |

| `add_career_values` | 同上 | 同上（还涉及列名 `value_id`/`value_test_time`） |
| `get_user_by_studentname` | `")" 附近有语法错误` | **真·代码 bug**：`WHERE )` 缺列名，与库无关 |
| `get_jobs_by_criteria` | `"}" 附近有语法错误` | 误报：SQL 是运行时 f-string 拼的 |

### 4.2 新库失败的 55 条

53 条是「对象名无效」——接口用的 14 张表在新库里一个都不叫这个名字（新库叫 `user`/`student_info`/`job_library`…）。
其余 2 条与旧库同源：`get_user_by_studentname`（真 bug）、`get_jobs_by_criteria`（f-string 误报）。
`get_day_plans_by_student` 在新库归入「对象名无效」，因为 `day_plans` 表本身就不存在。

**所以：旧库的问题是 4 个名字 + 1 个列宽 + 1 个缺列；新库的问题是整套命名。**

## 10. 对方案的影响（结论不变，依据更硬）

1. **改库优于改代码**：真正的差异只有 4 个名字 + 2 个列宽 + 1 个缺列，其余 51 条 SQL 已经成立。
2. **新库不能靠改名对齐**：55 条失败里 53 条是对象名，且 6 处是结构性差异（列转行、拆表、多值变单值、无企业表）。
3. **推荐层要接受降级**：兴趣维度恒 100，不是 0；剩下 65% 权重有真实数据。
4. **改名是安全的**：视图、存储过程、21 条 CHECK、5 条唯一约束都不受影响，已在事务内验证。
