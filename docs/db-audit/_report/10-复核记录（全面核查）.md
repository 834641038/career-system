## 一、核查方法

| 路径 | 做法 | 能查什么 | 局限 |
|---|---|---|---|
| A. AST 解析 | `ast.parse` 解析 `database_interface.py`，统计 class / 方法 / `query=` 赋值 / `_execute_*` 调用 | 方法数与 SQL 数的权威口径 | 不校验 SQL 语义 |
| B. 静态表列检查 | 正则提取 SQL，解析表名与列名，对照 `sys.tables` / `sys.columns` | 断表、断列（不受参数影响） | 查不出纯语法错误 |
| C. 编译校验 | `sp_describe_first_result_set` | 语法、对象、类型 | 参数占位符替换会产生假阳性 |
| D. 双口径行数 | `COUNT(*)` vs `sys.dm_db_partition_stats` | 真实行数、统计陈旧 | 无 |
| E. 逐行扫描 | 按物理行扫描 `query =` | 防正则漏匹配（如 f-string） | 无 |

### 已排除的假阳性（不计入结论）

- `?` → `NULL`：`DATEADD(DAY, -NULL, GETDATE())` 报错，误判 `day_plans` 查询有缺陷
- `?` → `1`：向 `datetime` 列与带 CHECK 的列插数字，多出 5 条假失败

**结论：编译校验不能单独用于判定接口缺陷，必须配合静态检查。**

### 已排除的统计陷阱

- `max_length` 对 `nvarchar` 是**字节数**，字符数须 ÷2。我此前多份文档直接把它当字符数，导致宽度全部写大一倍（见 E6）。
- `sys.partitions.rows` 在回滚后是**陈旧值**。实测本次 `job_library` 统计为 43、实际 `COUNT(*)` 为 3。
