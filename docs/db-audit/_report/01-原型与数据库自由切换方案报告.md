## 0. 先纠正上一份报告的三处错误

在动手设计之前，必须先把事实摆正。上一份《数据库接口对齐核查报告》里有三处结论不成立，本报告以实测为准：

| # | 上一份报告的说法 | 实测事实 | 影响 |
|---|---|---|---|
| 1 | 「两库都没有自增主键，15 个 INSERT 必然失败」 | **错误**。用 `sys.columns.is_identity` 逐列核对：`career_recommendation` 14/14 张、`career_system` 24/24 张，**主键全部是 IDENTITY**。之前判成「无自增」是因为跨库调用 `OBJECT_ID()` 返回 NULL | 两库的插入都不存在主键生成问题，方案可以大幅简化 |
| 2 | 「旧库 15 张表」 | **错误**，是 **14 张** | 统计口径 |
| 3 | 「接口 26 条 SQL 在旧库只有 2 条失败」 | 方向对，但**少算了**：实际 4 条因表名失败（2 张表 × 各 2 个方法），另有 3 条是别的原因 | 见第 2 节 |

我把 `database_interface.py` 里**全部 58 条 SQL** 用 `sys.sp_describe_first_result_set` 逐条编译（不执行、不写库），结果：

| 目标库 | SQL 总数 | 失败 | 失败原因分布 |
|---|---|---|---|
| `career_recommendation` | 58 | **7** | 表名不存在 4 条 / 代码本身残缺 1 条 / 动态拼接 1 条 / 参数类型推断 1 条 |
| `career_system` | 58 | **55** | 55 条全部是「对象名无效」——接口用的 14 张表在新库一个都不叫这个名字 |

**结论：旧库离「能用」只差 4 个名字、1 个列宽和 1 个权限。** 新库则是换了一套模型，不是改名能解决的。

### 0.1 而且——系统现在**根本没连过库**，这是有代码证据的

`DatabaseInterface.__init__` 的凭证是 `app_user / career_recommendation`。实测这个登录：

```
登录名 app_user 存在，default_database_name = career_recommendation
career_system 内：有用户映射，角色 db_datareader + db_datawriter  → 能连
career_recommendation 内：**没有任何用户映射**                    → 登录失败
```

报错链：`无法打开登录所请求的数据库 "career_recommendation" (4060)` → `用户 'app_user' 登录失败 (18456)`。

于是 `__init__` 走 `except` 分支 → `use_sqlserver = False` → `_init_sample_data()`。

**也就是说：所谓「原型和数据库不连接」，不是设计上没接，是连接直接失败后静默降级了。** 而且降级后 `self.users = {}`，内存里连一个账号都没有——所以现在能注册能登录，全靠运行期内存，**重启即全部丢失**。

这条决定了执行顺序：**必须先建用户映射（D0），但建完立刻会切换行为**，所以 D4（列宽）、D6（student_id）、密码重置必须同批完成，否则一开就登不进。

## 1. 一句话结论

> **把 `career_recommendation` 的 2 个表名、3 个列名改掉，放宽 2 个列宽、补 1 个外键列，再给 `app_user` 建一个数据库用户映射（共 7 处 DDL + 1 处权限），接口层的 58 条 SQL 就能全部成立（实测 55/58，剩 3 条是代码 bug 与静态误报）；然后在 `database_interface.py` 里加 1 个开关变量 + 3 个门面函数，`backingend_API.py` 只改 1 行 import，即可在「样本数据」和「SQL Server」之间自由切换。**

但必须同时说清楚：**「自由切换」在两层的含金量不一样。**

- **CRUD 层（登录、注册、资料、计划、技能、匹配）→ 100% 等价**，切过去就是真的在读写库。
- **推荐层（实习/课程/路径）→ 结构等价、数据降级**：旧库有真数据的是**技能 30% + 学业 20% + 偏好 15% = 65% 权重**；**霍兰德 35% 权重两端都缺数据**（学生测评表 0 行、岗位没有兴趣权重列），课程目录和路径模板**没有表**。

## 3. 要改的对象：7 处 DDL + 1 处权限

### 3.1 必改（不改就跑不通）

| # | 对象 | 现状 | 改为 | 依据 |
|---|---|---|---|---|
| **D0** | 数据库用户 | `app_user` 在 `career_recommendation` **无映射** | `CREATE USER [app_user] FOR LOGIN [app_user]` + 加入 `db_datareader`、`db_datawriter` | 不建就 4060/18456，接口永远连不上（见 0.1） |
| **D1** | 表 `holland_tests` | 表名是 `holland_tests` | `holland_test_results` | 接口 2 条 SQL 写死此名 |
| **D2** | 表 `work_values` | 表名是 `work_values` | `career_values` | 接口 2 条 SQL 写死此名 |
| **D3** | 列 `work_values.worth_test_time` | `worth_test_time` | `value_test_time` | `SELECT ... ORDER BY value_test_time DESC` 与 `INSERT (... value_test_time)` 都用了这个名字 |
| **D4** | 列 `users_login.password_hash` | **`nvarchar(20)`**（`sys.columns.max_length=40` 字节） | `nvarchar(255)` | 接口用 SHA-256 十六进制 = **64 字符**，20 装不下。实测插入 64 字符直接报错 `3621 语句已终止` |
| **D4b** | 列 `users_login.user_email` | `nvarchar(40)` | `nvarchar(100)` | 真实邮箱超 40 字符会被拒；存量 `stu_0001@career.edu.cn` 仅 22 字符，所以现在没暴露 |

D1、D2 是纯改名，**不动数据、不动外键**（这两张表当前 0 行，零风险）。
D3 在 D2 之后执行。D4 只放宽长度，不影响存量（存量全是 9 字符）。

### 3.2 建议改（不改不影响跑通，但影响正确性）

| # | 对象 | 现状 | 改为 | 原因 |
|---|---|---|---|---|
| **D5** | 列 `work_values.worth_id` | `worth_id` | `value_id` | 接口内存分支用 `value_id` 做键，DB 分支 `SELECT *` 会把主键叫 `worth_id`，两模式返回的键名不一致 → 切换时前端拿到的主键名会变 |
| **D6** | 列 `users_login.student_id` | **不存在** | 新增 `int NULL` + 回填 | 见下方专项说明 |

**D6 专项说明（这是「登录后拿不到学生」的根因）**

`backingend_API.py` 的 `resolve_student_id()` 读的是 `user.get('student_id')`，但 `users_login` 没有这一列，`students` 也没有反向往账户上写。结果是：

- 登录成功 → JWT 里带 `user_id` → 接口查 `users_login` → 拿不到 `student_id` → 返回 `None` → 一路兜底到写死的 `DEFAULT_STUDENT_ID = '2024001'`
- 而旧库真实学生 ID 是 `2400001` 起（7 位），`2024001` 是 7 位但**不存在** → 推荐接口 404
- 所有账号看到的是同一个（不存在的）学生

两种修法：

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A. 改库（推荐）** | `users_login` 加 `student_id int NULL`，`UPDATE ... FROM students WHERE students.user_id = users_login.user_id` 回填 20 行 | 1 列 + 1 条 UPDATE | 反规范化，后续要保证注册时同步写入 |
| B. 改代码 | `resolve_student_id` 改成 `SELECT student_id FROM students WHERE user_id = ?` | 改 1 处代码 | 无冗余，但要动代码 |

**旧库的 `students.user_id` 是 1~20，正好和 `users_login.user_id` 一一对应，回填是确定的，不需要猜。**

### 3.3 不建议改的一处

`users_login.last_Login_time`（大写 L）与接口的 `last_login_time` 大小写不同——**SQL Server 默认排序规则大小写不敏感，这不是问题**，不要动。

### 3.4 推荐层专用（CRUD 不需要，但切过去后推荐要用）

| # | 对象 | 现状 | 建议 | 说明 |
|---|---|---|---|---|
| **D7** | `jobs` 的霍兰德权重 | **没有** | 加 `holland_R/I/A/S/E/C` 六列 `tinyint NULL` | 算法的 `holland_match` 是 `{'I':0.7,'C':0.2,'E':0.1}` 这种**每岗不同**的权重；没有这六列，两端权重都为空 → 距离 0 → **该项恒为满分 100**（实测，不是 0 分） |
| **D8** | 课程目录 | **没有表** | 新建 `course` 表（8 门课的量级） | 课程推荐的输入之一 |
| **D9** | 职业路径模板 | **没有表** | 新建 `career_path_template` 表（2 条路径） | 路径推荐的输入 |

D7–D9 是**加东西**，不是改名。放不放进这次改动，见第 9 节的决策点。

## 5. 为什么「改完名字」还不能直接切

这是本次方案最关键的一节。

`database_interface.py` 返回的是**扁平行**（`{'student_id':2400001,'student_name':'张明',...}`），而三个推荐算法的入参是**嵌套画像**（`student['basic_info']['gpa']`、`job['required_skills']['必需技能']`）。两者不是同一个东西。

**如果只改名就切换，推荐接口会直接 `KeyError: 'basic_info'` 崩掉。**

所以「接口处那一项」不只是个 if/else，还需要一层**形状适配**——把行拍成算法要的嵌套结构。这不是重写算法，只是搬字段。

### 5.1 学生画像的逐字段映射（旧库实测确认）

| 算法要的路径 | 旧库来源 | 现状 |
|---|---|---|
| `basic_info.name` | `students.student_name` | ✅ 20 行有值 |
| `basic_info.major` | `students.student_major` | ✅ |
| `basic_info.grade` | `students.grade` | ✅ |
| `basic_info.gpa` | `students.gpa` | ✅ |
| `holland_scores.{R..C}` | `holland_test_results` 最新一行 | ❌ **表 0 行** |
| `holland_code` | 由 `holland_scores` 降序取前 3 拼串 | ⚠️ 依赖上一行 |
| `skills.{category}.{name}.level` | `student_skills.proficiency_level` JOIN `skills.skill_category/skill_name` | ✅ 40 行，20 个学生全覆盖 |
| `skills.{...}.certified` | 无此列 | ⚠️ 固定 `False` |
| `academic_records.courses_completed` | 无表 | ❌ 空数组 |
| `academic_records.projects` | `experiences` where `experience_type='项目'` | ❌ 表 0 行 |

## 6. 切换开关的设计（本次唯一要改代码的地方）

### 6.1 设计原则

1. **默认值保持现状**——`prototype`，不改默认行为，任何人不设环境变量时系统照旧跑。
2. **一处声明**——所有分支判断只读一个变量，不散落在业务里。
3. **签名不变**——`backingend_API.py` 只改 import 的来源，函数名、参数、返回结构全不变。
4. **切换不改调用方**——3 个推荐端点、4 个数据函数一行都不用动。

### 6.2 具体做法

**（1）`database_interface.py` 顶部加一个开关（1 处声明）**

```python
import os

# ============ 数据源开关：原型 / 数据库 ============
# prototype = 读 sample_data.py 里写死的样本（默认，保持现状）
# database  = 读 SQL Server career_recommendation
# 切换方式：环境变量 CAREER_DATA_SOURCE=database；或在 .env 里加一行
DATA_SOURCE = os.getenv("CAREER_DATA_SOURCE", "prototype").strip().lower()
```

**（2）同文件末尾加 3 个门面函数（签名与 `sample_data` 完全一致）**

```python
def get_student_profile(student_id):
    if DATA_SOURCE == "prototype":
        from sample_data import get_student_profile as _f
        return _f(student_id)
    return _student_profile_from_db(student_id)      # 按 5.1 的表搬字段

def get_filtered_jobs(filters):
    if DATA_SOURCE == "prototype":
        from sample_data import get_filtered_jobs as _f
        return _f(filters)
    return _jobs_from_db(filters)                     # 按 5.2 的表搬字段

def get_jobs_by_ids(job_ids):
    ...  # 同上

def get_course_catalog():
    if DATA_SOURCE == "prototype":
        from sample_data import get_course_catalog as _f
        return _f()
    return _courses_from_db()                         # 无表时返回 [] 并打日志
```

**（3）`backingend_API.py` 只改 1 处 import**

```python
# 改前（第 6-9 行）
from sample_data import (
    get_student_profile, get_filtered_jobs, get_jobs_by_ids,
    get_course_catalog, CAREER_PATHS_DATABASE
)

# 改后（同一位置，1 处）
from database_interface import (
    get_student_profile, get_filtered_jobs, get_jobs_by_ids,
    get_course_catalog, CAREER_PATHS_DATABASE
)
```

> `CAREER_PATHS_DATABASE` 在 `database_interface` 里原样 re-export 即可，路径模板暂不切库（库无此表）。若后续建了 `career_path_template` 表，再换成 `get_career_paths()`，仍只改这 1 行。

### 6.3 改动量盘点

| 文件 | 改动 | 行数 |
|---|---|---|
| `database_interface.py` | 加开关 1 处 + 门面 4 个 + DB 侧搬字段 3 个 | 约 +160 行，**不改原有 50 个方法任何一行** |
| `backingend_API.py` | import 换来源 | **1 处，5 行** |
| `sample_data.py` | 不动 | 0 |
| 三个推荐算法 | 不动 | 0 |
| 数据库 | 6 处 DDL（+3 处可选） | — |

## 7. 切换后的等价性矩阵

| 功能 | 走哪条路 | 切到 database 后 |
|---|---|---|
| 注册 / 登录 / 改密 | `db.add_user` / `get_user_by_*` | ✅ 完全等价（需先做 D4、D6） |
| 个人资料 `/api/auth/profile` | `db.get_user_by_id` | ✅ 等价（D6 后能返回 studentId） |
| 日计划 / 周计划 CRUD | `db.add_day_plan` 等 | ✅ 等价（两表 0 行，可正常写入） |
| 技能、经历、匹配结果 | `db.*` | ✅ 等价 |
| **实习推荐** | 适配层 → 算法 | ⚠️ **部分降级**：技能/学业/偏好三项真算；霍兰德项恒为满分 100（无区分度） |
| **课程推荐** | 适配层 → 算法 | ❌ **不可用**：库无课程表，返回空列表 |
| **职业路径推荐** | 仍读样本模板 | ⚠️ 仍用原型（模板不在库里），只是学生画像换成真数据 |
| 计划板块的 `MEM_PLANS` / `MEM_TASKS` | 内存字典 | ⚠️ 与库无关，仍是内存（未接入 `day_plans`/`week_plans`） |

**一句话：切过去之后「系统能登录、能存数据、推荐能算」，但「兴趣维度」和「课程/路径」是缺的，不是坏的。**

## 8. 风险与回滚

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|

## 10. 建议执行顺序（等你确认后再动）

1. **备份**：已完成（两个 .bak）。
2. **建回滚脚本**：先写好 `rollback.sql`（改回旧表名、删新建的列、删数据库用户），再执行正向脚本。
3. **执行 D1–D5**：2 个表名 + 2 个列名 + 1 个列宽。（此时系统行为**不变**，因为还连不上）
4. **执行 D6**：加 `student_id` 列 + 回填 20 行。
5. **重置 20 个账号密码**（决策点 3）：存量 9 字符哈希与 SHA-256 不兼容，不重置则建完 D0 全员登不进。
6. **最后执行 D0**：建 `app_user` 用户映射。**这是唯一会立刻改变系统行为的动作**，必须放在最后一步，且前 5 步全部验证过。
7. **跑回归**：58 条 SQL 应全部通过（除那条残缺 SQL）。
8. **改代码**：`database_interface.py` 加开关 + 门面；`backingend_API.py` 换 import。
9. **双模式对跑**：同一学生分别在 `prototype` / `database` 下调用三个推荐接口，比对字段完整性与分数。

> ⚠️ 顺序不能颠倒：D0 一旦执行，接口就会真的去查库。此时若 `password_hash` 还是 `nvarchar(20)`、`student_id` 还不存在、密码还是 9 字符，系统会从「能跑但用的是假数据」变成「真实地跑不起来」。
