## 0. 判定依据（三条硬证据，不是名字像不像）

**证据 A：接口对 12/14 张表用 `SELECT *`，行转 dict 后上层按键取值。**
`database_interface.py` 里 `SELECT *` 出现 24 次，覆盖 12 张表：

```
users_login(4) skills(3) jobs(3) week_plans(2) students(2) student_preferences(2)
day_plans(2) companies(2) student_skills(1) holland_test_results(1) experiences(1) career_values(1)
```

=> 对这些表，接口的隐含契约 = **旧表全部列**。少一列，上层就拿不到那个 key。

**证据 B：推荐算法对三个字段做数值比较与算术，文本会直接崩。**

`internship_recommender.py`：
```python
if student_level >= required_level:                       # 数值比较
    required_score += 1 + 0.1 * (student_level - required_level)
else:
    required_score += student_level / required_level * 0.6  # 算术
```
`career_path_planning.py`：`current_grade = ...get('grade', 2)`、`gpa = ...get('gpa', 0)`

=> `grade`、`required_level`、`proficiency_level` **必须是数字**。
新库现在存的是 `大二`、`proficient`，若直接沿用，算法会 `TypeError`。

**证据 C：老账号不迁。**
旧库 `users_login` 20 条账号存的是明文 `passwd123`，按决策不迁。
=> `students.user_id` 只能置 NULL；而 SQL Server 唯一约束**只允许一个 NULL**，
所以 `UQ_student_user`、`UQ_student_email`、`UQ_student_number` 必须去掉。

## 2. 列级对照（逐列，含动作依据）

### 2.1 users_login（原 `user`）

| 旧库列 | 新库原列 | 动作 | 依据 |
|---|---|---|---|
| user_id | user_id | 保留 | 主键自增 |
| user_name | —（无） | **新增** nvarchar(100) | 接口按 `WHERE user_name=?` 登录；现有账号取邮箱 @ 前缀回填 |
| password_hash | password_hash | 改类型 varchar→nvarchar(255) | 旧库 **nvarchar(20)**（`max_length=40` 字节 ÷2），存不下 SHA-256 的 64 字符；新库本是 `varchar(255)`，改 nvarchar 是为中文兼容，**不是放宽** |
| user_email | email | **改名** | 接口 INSERT/SELECT 都用 `user_email` |
| user_status | —（无） | **新增** tinyint NOT NULL DEFAULT 1 | 接口注册写该列 |
| user_created_time | create_time | **改名** + datetime2(7) | 接口写 `user_created_time` |
| last_Login_time | last_login_time | 保留 | 仅大小写差异，排序规则不区分大小写 |
| user_remark | —（无） | **新增** nvarchar(1000) | 接口注册写该列 |

### 2.2 students（原 `student_info`）

| 旧库列 | 新库原列 | 动作 | 依据 |
|---|---|---|---|
| student_id | student_id | 保留 | 主键 |
| student_name | name | **改名** + 放宽 NULL | 接口 `SELECT *` 后取 `student_name` |
| student_major | major | **改名** + 放宽 NULL | 同上 |
| grade | grade | **varchar→tinyint**，值 `大二→2` | 算法按数字比较 |
| gpa | gpa | 改 decimal(3,2) | 旧库 decimal(3,2) |
| user_id | user_id | **NOT NULL→NULL** | 老账号不迁 |
| （无） | student_number | 放宽 NULL + 去唯一约束 | 旧库无此列；唯一约束只容一个 NULL |
| （无） | email | 放宽 NULL + 去唯一约束 | 同上 |

### 2.3 skills（原 `skill_library`）
`skill_id` 保留；`skill_name` varchar→nvarchar(100)（去 UQ 后重建）；`skill_category` varchar→nvarchar(40)；
`skill_description` ← `description` 改名，nvarchar(max)。

### 2.4 holland_test_results（原 `holland_assessment`）
8 列改名：`holland_id→holland_test_id`、`test_time→holland_test_time`、
`r_score→holland_R`、`i_score→holland_I`、`a_score→holland_A`、`s_score→holland_S`、`e_score→holland_E`、`c_score→holland_C`；
六维分收紧 `tinyint NOT NULL`，时间 `datetime NOT NULL`（照旧库）。

### 2.5 career_values（原 `value_assessment`）
`value_assess_id→worth_id`、`test_time→worth_test_time`；
**新增 6 维宽列**：`social_contribution / achievement_oriented / safe_stable / work_life_balance / power_status / innovation_challenge`（均 tinyint NULL）。
> 说明：新库把 6 维拆到 `value_assessment_detail` 明细表，但接口 `SELECT * FROM career_values` 取宽表 → 必须补宽列。
> 设为 NULL 而非 NOT NULL：写主表时可能只写主从结构，强制 NOT NULL 会挡住插入。

### 2.6 jobs（原 `job_library`）
`job_title` varchar→nvarchar(200)（去索引后重建）；`job_type` varchar→nvarchar(40)；
**新增 `company_id`** int（迁后收紧 NOT NULL + 外键→companies）；
**新增 `salary_range`** nvarchar(100)。
> `company_id` 与 `salary_range` 是接口 `JOIN companies`、展示薪资的必需列，新库原本没有；
> 新库的 `industry_id` / `education_requirement` 是**另一个概念**，不替代这两列。

### 2.7 job_skill_requirements（原 `job_skill_requirement`）
`requirement_id/job_id/skill_id` 保留；
`required_level` **varchar→tinyint**，值 `basic→3 / proficient→4 / expert→5`；
**新增 `requirement_type`** nvarchar(20)（必需/加分，接口 3 处引用）。

### 2.8 matching_results（原 `job_match`）
`match_id/student_id/job_id` 保留；`match_score` **NOT NULL→NULL**，decimal(5,2)（照旧库）；
新库独有 `match_time` 保留。

### 2.9 week_plans（原 `weekly_task`）
`weekly_task_id→week_plan_id`、`weekly_task_name→week_plan_name`、`start_time→week_plan_start`、`end_time→week_plan_ddl`；
**新增 `week_plan_finish`** tinyint NOT NULL DEFAULT 0，由 `completion_percentage>=100` 折算；
时间列收紧 datetime NOT NULL（先去索引后重建）。

### 2.10 day_plans（原 `daily_task`）
`daily_task_id→day_plan_id`、`daily_task_name→day_plan_name`、`task_content→day_plan_describe`、
`priority→day_plan_prority`、`end_time→day_plan_ddl`、`is_completed→day_plan_finish`；
`day_plan_prority` **varchar→tinyint**，值 `高→1 / 中→2 / 低→3`（先删 CHECK 与默认约束）；
`day_plan_finish` **bit→tinyint NOT NULL DEFAULT 0**（先删默认约束与索引，迁后重建）。

### 2.11 新建 4 张表（列名照接口，宽度比旧库宽一倍）

> 下列 `nvarchar(N)` 是**字节数口径**（`max_length` 原值），真实字符数为 N÷2。
> 旧库对应列为：company_name 100 / company_location 50 / company_size 20 / expected_salary 50 / work_mode_preference 20 / experience_title 100 字符。
> 脚本实际建的宽度是旧库的 2 倍，**只会更宽松，不会截断**。

- `companies`：company_id IDENTITY PK / **company_location** / **company_size** / **company_description**　（列名必须用带 `company_` 前缀的全称，接口 INSERT 明确点名）
- `student_skills`：skill_record_id IDENTITY PK / student_id / skill_id / proficiency_level tinyint / experience_months int
- `student_preferences`：preference_id IDENTITY PK / student_id / preferred_industries nvarchar(max) / preferred_locations nvarchar(max) / expected_salary / work_mode_preference
- `experiences`：experience_id **IDENTITY** PK / student_id / experience_title / experience_content nvarchar(max) / experience_type varchar(50) NOT NULL / experience_role varchar(50) / experience_start_time date NOT NULL / experience_end_time date / updated_time datetime
  > 旧库 `experience_id` 实测 `is_identity=1`，**本来就是自增**。新建照抄 IDENTITY 即可，不存在「修正」。

### 2.12 新库独有、接口不用 → 一律保留
`students` 的 gender/birthday/phone/university/bio/avatar_url/enrollment_year/expected_graduation/gaokao_score/current_location/desired_location/desired_industry_id；
`jobs` 的 industry_id/education_requirement/holland_code/job_description；
`weekly_task` 的 priority/task_type/completion_percentage/target_skill_id/current_proficiency_level；
`daily_task` 的 task_type/target_skill_id/current_proficiency_level；
以及 `certificate/achievement/competition_award/career_plan/study_time/industry/skill_assessment(+detail)/value_assessment_detail/values_library/job_value_requirement/internship_experience/project_experience/campus_activity`。

| 目标表 | 来源 | 行数 | 转换 |

| companies | companies | 9 | ID 原样（IDENTITY_INSERT） |

| jobs | jobs | 23 | 带 company_id / salary_range |

**不迁移**：旧库 20 个明文密码账号（按决策不迁）。

**带原 ID 迁移的原因**：`student_skills / job_skill_requirements / matching_results / jobs.company_id`
都以这些 ID 做外键，重编号会断链。故用 `SET IDENTITY_INSERT ON` 保留旧 ID（旧库 ID 在 2400001+ 段，新库种子在 1–15 段，**完全错开**）。

> ## ⚠️ 清种子并非必需，且代价很大（2026-11-04 核查结论）
>
> 现脚本的 `DELETE FROM (career_values, students, skills, jobs, skill_assessment, companies)` 会因 `CASCADE` 删掉新库 **72 行**演示数据，只剩 `user` 1 + `industry` 4 + `values_library` 5 = **10 行**。具体包括：
> - 价值观 1 主 + 5 明细（**与「先留着」决策冲突**）
> - 张三的证书 2 / 成就 4 / 竞赛 2 / 计划 2 / 学习时长 4 / 技能测评 1+15 / 霍兰德 1
> - 实习 1 / 项目 2 / 周计划 1 / 日计划 3 / 匹配 2
> - 经历 3 行种子（若清掉，就无法再「复制进 experiences」）
>
> **而旧库 ID（2400001+）与新库种子 ID（1–15）完全不冲突，直接叠加即可。**
> 是否清种子需重新决策，详见 `10-复核记录（全面核查）.md` 第三节。
