> 本文档取代 06 号的"单纯改名"思路。用户最终决策是：
> **先补新库相对旧库缺失的字段/表，再改名对齐接口契约，并迁移数据，保持可用性完整。**
> 对照原则由用户明确指定：**按接口代码实际读写哪些列来定，而不是按表名列名相似度去猜。**

## 0. 方法论：什么叫"按实际系统使用情况对照"

我用脚本从 `database_interface.py` 抽取了所有 SQL 字符串里 `FROM / INTO / UPDATE / JOIN` 引用的表，
以及 `tbl.col` 形式点名的列，得到**接口契约事实**：

- 接口**只引用 14 张表**，且接口 SQL 里出现的表名，与本次要改名/新建的 14 张表**逐一吻合**，
  没有任何一张是"看着像就改"的——改名/新建清单本身就是接口用法推导出来的。
- 逐列核对：凡是接口 SQL 实际 SELECT/INSERT/UPDATE 的列，新库没有或名字不同的，才做"加列/改名"；
  新库有、接口不用的列和表，一律**保留不动**（避免无谓破坏规范化骨架）。

抽取结果（接口引用频次 → 表）：

```
skills(13) students(12) users_login(10) jobs(10) companies(9)
student_skills(8) day_plans(7) student_preferences(6) experiences(5)
week_plans(5) job_skill_requirements(4) holland_test_results(3)
career_values(3) matching_results(3)
```

这 14 张表 = 迁移处理的全部对象。下面每一节都回到"接口到底用了哪一列"来论证。

## 2. 新库相对旧库"缺什么"——用法驱动结论

### 2.1 整表级：新库缺 4 张接口必用表

| 接口必用表 | 旧库 | 新库现状 | 动作 |
|---|---|---|---|
| `companies` | 有（9 家） | **无** | **新建**（导旧库 9 家） |
| `student_skills` | 有（40 条） | **无** | **新建** |
| `student_preferences` | 有（20 条） | **无** | **新建**（列与旧库完全一致） |
| `experiences` | 有（统一表，0 行） | **无**（新库反而有 3 张分表 internship/project/campus，接口完全不用） | **新建统一表**（对齐接口 9 列） |

> 关键修正（相对 06 号）：旧库经历是**一张统一表** `experiences`（用 `experience_type` 区分实习/项目/校园），
> 新库是 3 张分表且列名与接口不一致。正确做法是**按接口新建统一 `experiences`**。
> 新库那 3 张分表（1+2+0 行）接口不引用，保留无害，可不处理。

### 2.2 列级：新库现有表缺的接口必用列 / 需改名

**A. 缺列（接口用、新库没有，必须加）**

| 表 | 缺的列 | 接口为何需要 | 类型 |
|---|---|---|---|
| `jobs` | `company_id` | 推荐联表 `JOIN companies`、展示所属公司 | int NULL |
| `jobs` | `salary_range` | 岗位薪资展示 / 写入 | nvarchar(100) NULL |
| `job_skill_requirements` | `requirement_type` | **必需(70%权重)/加分 区分**，算法真用（3 处） | nvarchar(20) NULL |
| `users_login`(原`user`) | `user_name` | 登录名（接口用 `user_name` 登录，旧库是 `stu_0001` 这类） | nvarchar(50) NULL |
| `users_login` | `user_status` | 账号启用状态 | tinyint NULL 默认 1 |
| `users_login` | `user_remark` | 备注 | nvarchar(max) NULL |

**B. 改名（接口用旧名、新库用了不同名，必须 rename）**

| 表 | 新库原名 → 接口名 |
|---|---|
| `users_login` | `email`→`user_email`，`create_time`→`user_created_time`（`last_login_time` 同名不动） |
| `students`(原`student_info`) | `name`→`student_name`，`major`→`student_major` |
| `skills`(原`skill_library`) | `description`→`skill_description` |
| `holland_test_results`(原`holland_assessment`) | `holland_id`→`holland_test_id`，`test_time`→`holland_test_time`，`r_score`→`holland_R` …（六维 R/I/A/S/E/C） |
| `career_values`(原`value_assessment`) | `test_time`→`value_test_time` |
| `week_plans`(原`weekly_task`) | `weekly_task_id`→`week_plan_id`，`weekly_task_name`→`week_plan_name`，`start_time`→`week_plan_start`，`end_time`→`week_plan_ddl` |
| `day_plans`(原`daily_task`) | `daily_task_id`→`day_plan_id`，`daily_task_name`→`day_plan_name`，`task_content`→`day_plan_describe`，`priority`→`day_plan_prority`，`end_time`→`day_plan_ddl`，`is_completed`→`day_plan_finish` |

**C. 改类型 / 放宽约束（保证接口能写）**

| 表 | 调整 | 原因 |
|---|---|---|
| `students` | `grade` tinyint→varchar（存 `大二/大三/大四`）；`user_id` 由 NOT NULL 放宽 NULL；`student_number/email` 等唯一约束删除（避免注册 515） | 旧库 grade 是 2/3/4 枚举；老账号不迁后 user_id 可为空；注册只写 5 列 |
| `jobs` | `job_title/job_type` 由 varchar 改 nvarchar | 中文岗位名防乱码 |
| `skills` | `skill_name/skill_category` 由 varchar 改 nvarchar | 中文技能名防乱码 |
| `users_login` | `password_hash` 由 nvarchar(20) 扩到 nvarchar(255) | SHA-256 哈希 64 字符装不下 20 |
| `day_plans` | 删 `priority` 上的 CHECK（低/中/高）与默认约束后再改名 | 改名/改类型前的依赖清理 |

### 2.3 反过来的"多出来"：新库有、接口不用的（一律保留，不动）

`certificate / achievement / competition_award / career_plan / study_time / industry /
skill_assessment(+detail) / value_assessment_detail / values_library / job_value_requirement /
internship_experience / project_experience / campus_activity` 等。
它们属于规范化骨架的"富余"，接口当前不碰，**保留即保留未来演进能力**，迁移不删。

## 3. 逐表字段对照（用法驱动明细）

> 说明：下表"接口列"= 第 1 节事实；"新库对齐"= 该列在新库最终形态的动作。

### 3.1 users_login（原 `user`）
| 接口列 | 新库对齐 | 说明 |
|---|---|---|
| user_id | keep 主键自增 | |
| user_name | **add** nvarchar(50) | 登录名 |
| password_hash | convert nvarchar(255) | 原 20→255，存 SHA-256 |
| user_email | rename（原 email） | |
| user_status | **add** tinyint 默认1 | |
| user_created_time | rename（原 create_time） | |
| last_login_time | keep | |
| user_remark | **add** nvarchar(max) | |

### 3.2 students（原 `student_info`）
| 接口列 | 新库对齐 |
|---|---|
| student_id | keep 主键 |
| student_name | rename（原 name） |
| student_major | rename（原 major） |
| grade | convert tinyint→varchar（2/3/4→大二/大三/大四） |
| gpa | keep（decimal 值域 3.1–3.9 无损） |
| user_id | widen NOT NULL→NULL（老账号不迁） |

### 3.3 skills（原 `skill_library`）
skill_id keep；skill_name/skill_category convert varchar→nvarchar；skill_description rename（原 description）。

### 3.4 jobs（原 `job_library`）
job_id keep；job_title/job_type convert→nvarchar；**company_id add**、**salary_range add**。

### 3.5 job_skill_requirements（原 `job_skill_requirement`）
requirement_id/job_id/skill_id keep；required_level keep（varchar 存 basic/proficient/expert）；
**requirement_type add**（必需/加分）。

### 3.6 student_skills / student_preferences / companies / experiences
四个新建表，列与接口第 1 节清单**完全一致**，其中：
- `experiences.experience_id` 设为 **IDENTITY**（接口 INSERT 不带该列，旧库非自增是潜在 bug，新建即修正）。
- 旧库 `student_preferences` 列名与新表完全相同，零转义。

### 3.7 matching_results / holland_test_results / career_values / week_plans / day_plans
均按第 1 节列名做 rename（见 2.2-B 与脚本阶段 3）。

## 4. 数据迁移映射

### 4.1 迁移清单（带旧 ID 迁入，外键才能对上）

| 目标表 | 来源 | 行数 | 值域转换 |
|---|---|---|---|
| skills | skills | 25 | 中文列改 nvarchar，ID 原样 |
| companies | companies | 9 | ID 原样 |
| students | students | 20 | `grade` 2/3/4→大二/大三/大四 |
| jobs | jobs | 23 | 带 company_id / salary_range |
| job_skill_requirements | 同名 | 46 | required_level 原样 |
| student_skills | 同名 | 40 | 原样 |
| student_preferences | 同名 | 20 | 原样 |
| matching_results | 同名 | 93 | 原样 |
| holland_test_results / career_values / week_plans / day_plans / experiences | 同名/新建 | 0 | 只迁结构（旧库这些表 0 行） |

> 旧库 experience_id 等非自增主键，迁入时 `SET IDENTITY_INSERT ON` 保留原 ID，
> 因为 `student_skills / job_skill_requirements / matching_results` 都以外键引用这些 ID。

### 4.2 不迁移的内容
- **老账号（旧库 20 个，明文 `passwd123`）**：按用户决策**不迁**，只保留新库已有 1 个账号（哈希占位）。
- **新库种子数据**：先按外键安全顺序 DELETE（daily_task 3 / holland_assessment 1 / job_library 3 /
  job_match 2 / job_skill_requirement 7 / skill_library 15 / student_info 1 / weekly_task 1 /
  value_assessment 1 / value_assessment_detail 5 等），再用旧库真实数据覆盖，避免主键/唯一冲突。
- **3 张经历分表 + 其他接口不用的表**：不动。

### 4.3 密码处理（边界）
- 旧库 `users_login.password_hash` 实际存的是**明文** `passwd123`，且无哈希——这 20 个账号不迁，问题消除。
- 新库保留那 1 个账号的占位哈希（`$2y$10$...`，bcrypt 风格），迁移不改它；
  真实上线时由注册/改密流程重写 SHA-256。

### 4.4 自增计数器
迁完带 ID 插入后，相关表自增计数器会被推到旧库最大值之上（如 user 8001、students 8002 等），
数据本身正确。是否 `DBCC CHECKIDENT ... RESEED` 归位，**待拍板**。

## 6. 待你拍板的 5 项

1. **经历 3 张分表**（新库 internship/project/campus，接口不用）是否保留？建议保留无害。
2. **价值观 5→6 维有损**：旧库 5 维，新库 6 维，`薪资回报` 无对应项只能丢；`work_life_balance/power_status` 留 NULL。是否接受？
